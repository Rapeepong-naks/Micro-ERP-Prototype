# ทดสอบ prototype กับผู้ใช้ร้านเสื้อผ้า

## วิธีส่ง

รัน `node prototype/build-test-site.cjs` และ `node prototype/check-test-site.cjs` จากโฟลเดอร์โปรเจกต์ แล้วนำโฟลเดอร์ `dist/user-test-site` ไปเผยแพร่เป็น static site. ในโฟลเดอร์นี้มี `index.html`, JavaScript, CSS และฟอนต์ครบ ไม่ต้องใช้ฐานข้อมูลหรือเซิร์ฟเวอร์ Node ระหว่างทดสอบ ไฟล์ `build.json` ระบุเวลาสร้างและตรวจได้ว่าตรงกับต้นฉบับล่าสุดหรือไม่

อัปโหลดโฟลเดอร์นี้ไปยังบริการ static hosting แล้วส่ง URL ที่ได้ให้ผู้ทดสอบ เปิดบนโทรศัพท์จริงได้ ไม่จำเป็นต้องใช้ Vercel เท่านั้น สำหรับการทดสอบในเครื่องตัวเอง ใช้ `node prototype/serve.cjs` แล้วเปิด `http://127.0.0.1:8765/`.

หน้าจอ HTML อ้างอิง `design/khonnai.figcraft` โดยใช้กรอบ 375 × 812 พิกเซลในพรีวิวบนคอมพิวเตอร์ และขยายเต็มจอเมื่อเปิดบนโทรศัพท์ ข้อมูลตัวอย่างถูกเติมไว้เพื่อให้ผู้ใช้ทำภารกิจจริงได้ จึงอาจมีข้อความหรือจำนวนการ์ดต่างจากเฟรมออกแบบที่เป็นสถานะว่าง

ข้อมูลใน prototype เป็นตัวอย่างและอยู่ในหน่วยความจำของเบราว์เซอร์เท่านั้น ผู้ทดสอบแต่ละคนเริ่มจากข้อมูลเดียวกัน การรีเฟรชหรือปิดหน้าเว็บทำให้ข้อมูลที่ลองกรอกหายไป จึงควรทำแต่ละภารกิจต่อเนื่องในรอบเดียว ไม่ใช้ข้อมูลลูกค้าจริง

รูปสินค้าที่เลือกจากเครื่องจะแสดงในสต็อกและแคตตาล็อกของหน้าที่เปิดอยู่ แต่ยังไม่ส่งไปยังผู้ทดสอบอีกเครื่องหนึ่ง การทดสอบแชร์แคตตาล็อกข้ามเครื่องควรใช้ภาพตัวอย่างที่ติดมากับเว็บ หรือรอระบบเก็บไฟล์จริงในระยะพัฒนาแอป

## สคริปต์ทดสอบ 20–25 นาที

บอกผู้เข้าร่วมว่า “ลองทำเหมือนกำลังใช้ร้านของคุณ พูดสิ่งที่กำลังคิดออกมาได้ ผมจะไม่บอกว่าต้องกดตรงไหน” ให้เปิดเว็บบนโทรศัพท์ของตนเองและแชร์หน้าจอหรือให้ผู้สังเกตจดสิ่งที่เกิดขึ้น

1. **หาของ:** ลูกค้าถามว่า A-215 ไซซ์ 34 สีดำขายได้กี่แพ็ก ให้ผู้ใช้หาคำตอบ
2. **จองของ:** ลูกค้าขอจอง A-215 ไซซ์ 34 สีดำ 2 แพ็ก สร้างการจองให้ลูกค้าใหม่
3. **สลับงาน:** ระหว่างกรอกการจอง ให้ไปดูสต็อกรุ่น A-102 แล้วกลับมาทำการจองต่อ ถามว่าคาดว่าจะกลับมาได้จากตรงไหน
4. **รับของ:** มีของ A-102 เข้ามา 2 แพ็ก บันทึกรับเข้า และตรวจว่ายอดสต็อกเปลี่ยน
5. **ปิดการขาย:** เปิดการจองที่ทำไว้ แล้วเปลี่ยนเป็นบิล ตรวจว่ายอดขายได้ลดลงตามที่คาด
6. **ตรวจข้อผิดพลาด:** ลองจองมากกว่าจำนวนที่ขายได้ ดูว่าข้อความเตือนเข้าใจหรือไม่
7. **แก้หลังบันทึก:** กลับไปที่รายการรับของที่เพิ่งบันทึก เปลี่ยนจำนวนหนึ่งรายการ แล้วดูว่ารู้หรือไม่ว่าสต็อกเปลี่ยนตามส่วนต่าง
8. **ยกเลิก:** เปิดรายการรับของหรือการจองที่ยังใช้งานอยู่ กดยกเลิก อ่านกล่องยืนยัน แล้วบอกก่อนกดว่าคิดว่าจะไปหน้าไหนและสต็อกจะเป็นอย่างไร

เพิ่มรอบทดสอบความเร็วสำหรับเจ้าของร้านคนเดียว: ให้เลือกรุ่นจากรายการยาวประมาณ 100 รุ่น ใส่ 20 ตัวเลือกสินค้าในบิลเดียว แล้ววัดเวลาตั้งแต่ค้นรุ่นแรกจนบันทึกบิลสำเร็จ เป้าหมายคือไม่เกิน 10 นาที ให้สังเกตว่าผู้ใช้เข้าใจช่องค้นหา ตัวกรองหมวด/หมวดย่อย ตะกร้าที่ยังเลือกค้างไว้ และรายการย่อก่อนยืนยันหรือไม่ ทดสอบรับของเข้าหลายรุ่นด้วยวิธีเดียวกัน

ตอนเพิ่มรุ่น ให้ผู้ใช้สร้างรุ่นไซซ์ตัวเลขและรุ่นไซซ์ตัวอักษรอย่างละหนึ่งรุ่น แล้วลองเพิ่มไซซ์ที่ไม่เข้ากับชุดที่เลือก ดูว่าข้อความตรวจข้อมูลช่วยแก้ได้หรือไม่ ลองสร้างหมวดย่อยใหม่และค้นรุ่นจากหมวดย่อยนั้น

เพิ่มโจทย์เปรียบเทียบสินค้า 2 แบบ: รุ่นแพ็กละ 3 ตัวที่แต่ละแพ็กเป็นสีเดียว ให้กรอกสต็อก 34 ดำ 3 แพ็กและ 34 ขาว 2 แพ็ก; รุ่นแพ็กละ 6 ตัวที่หนึ่งแพ็กคละสี ให้กรอกสต็อก 34 จำนวน 4 แพ็ก ถามผู้ทดสอบว่า “จุดเตือนของใกล้หมด 3 แพ็ก” หมายถึงอะไร และให้ทำนายยอดรวมแพ็ก/ตัวก่อนกดบันทึก ทดลองใส่เลขทศนิยมในช่องจำนวนเพื่อดูว่าเข้าใจข้อความตรวจข้อมูลหรือไม่

สลับลำดับข้อ 3 กับข้อ 4 ในผู้เข้าร่วมบางคนเพื่อดูว่าการนำทางยังเข้าใจได้เมื่อไม่ได้เดินตาม flow เดิม

## สิ่งที่บันทึก

ต่อภารกิจให้บันทึกว่า **สำเร็จเอง / สำเร็จเมื่อช่วย / ไม่สำเร็จ**, เวลาที่ใช้, จุดที่กดผิดหรือย้อนกลับ, คำพูดที่บ่งบอกความสับสน และหน้าที่ผู้ใช้คิดว่าข้อมูลหาย หลังจบรอบถาม 3 ข้อ: “เมนูไหนหายากที่สุด?”, “หลังบันทึกหรือยกเลิก ระบบพาไปตรงที่คาดไหม?”, “ถ้าใช้จริง สิ่งใดต้องแก้ก่อน?”

ทดสอบกับเจ้าของร้านและผู้ช่วยร้านอย่างละหลายคน โดยใช้ role switch ในหน้าแรก ก่อนสรุปผลให้แยกปัญหาที่เกิดซ้ำจากความชอบส่วนบุคคล แล้วแก้จุดที่ทำให้ภารกิจสำคัญไม่สำเร็จก่อน

## ขอบเขต prototype

ยังไม่มีบัญชีผู้ใช้ ฐานข้อมูล การซิงก์หลายเครื่อง และ LINE จริง ลิงก์แคตตาล็อกแสดงข้อมูลตัวอย่างของเบราว์เซอร์ผู้เปิด จึงใช้ทดสอบความเข้าใจหน้าจอและ flow ได้ แต่ยังใช้ทดสอบการทำงานข้ามผู้ใช้จริงไม่ได้
