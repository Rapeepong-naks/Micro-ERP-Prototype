# ทบทวนความยืดหยุ่นของ workflow

ตรวจวันที่ 27 ต.ค. 2569 เทียบ `GLOSSARY.md`, `.scratch/inventory-mvp/spec.md`, issue 08–16, ภาพ FigCraft และ `prototype/` ผู้ใช้ยืนยันว่ากลุ่มเป้าหมายคือร้านส่งเสื้อผ้าและธุรกิจที่คล้ายกัน ส่วนการแกะแพ็กขาย การคืนของ และการส่งของบางส่วนทำในระยะถัดไป

## คำตัดสิน

**ขอบเขตผลิตภัณฑ์ยังเหมาะกับ MVP ของกลุ่มเป้าหมายนี้** แกน “รุ่น → ตัวเลือกสินค้า → จำนวนแพ็ก → จอง/ขาย/รับเข้า/ปรับยอด” สอดคล้องกับงานของร้านส่งเสื้อผ้า ไม่จำเป็นต้องทำ workflow engine ที่ร้านกำหนดสถานะเองได้ในตอนนี้ แต่หน้าจอและต้นแบบกดได้บางส่วนยังยึดตัวอย่างร้านนำร่องมากเกินไป และต้องแยก “ข้อมูลตัวอย่าง” ออกจาก “กติกาที่บังคับกับทุกร้าน”

| ประเด็น | ปัจจุบัน | ข้อเสนอ |
|---|---|---|
| จำนวนตัวต่อแพ็ก | สเปกระบุว่าแตกต่างตามรุ่น แต่ต้นแบบกดได้มีชิป 3/6/10/12 เท่านั้น | ให้กรอกจำนวนเต็มบวกอื่นได้ด้วย; โหลแสดงเฉพาะเมื่อ 12 หารจำนวนตัวต่อแพ็กลงตัว |
| ไซซ์และสี | ต้นแบบกดได้มีรายการไซซ์/สีตายตัว | เพิ่มค่าที่ร้านใช้เองได้ และเลือกสีแยกตามไซซ์; ระบบต้องสร้างเฉพาะคู่ที่มีจริง |
| ราคาต่อไซซ์ | สเปกรองรับราคาแพ็กพิเศษตามไซซ์ แต่ต้นแบบกดได้ยังใช้ราคาเดียวต่อรุ่น | ในขั้นเพิ่มรุ่นมีราคาเริ่มต้นหนึ่งค่า และช่อง override เฉพาะไซซ์ที่ต่าง; บิลเก่าต้องเก็บราคาเดิม |
| รับของเข้า | สเปกต้องรับหลายรุ่นในบิลยี่ปั๊วใบเดียว | ต้นแบบกดได้ปรับให้เพิ่มหลายตัวเลือกสินค้าในรอบเดียวแล้ว; แอปจริงควรมีผลรวมและตรวจแต่ละบรรทัดก่อนบันทึก |
| การจอง | แกนจอง → บิลตรงกับการขายผ่าน LINE แบบร้านนำร่อง | ใช้คำทั่วไปบนข้อมูลคือ “การจอง” และเก็บที่มาของการจองเป็นข้อมูลประกอบ; อย่าผูกกติกาสต็อกเข้ากับ LINE โดยตรง |
| การจองค้าง | สเปกกำหนด 2 วันตายตัว | สำหรับ MVP ใช้ 2 วันได้ แต่ควรให้เห็นวัน/เวลาเริ่มจองและเรียงรายการค้าง; ตัดสินใจเรื่องตั้งค่าจำนวนวันหลังทดสอบร้านอื่น |
| สิทธิ์ | มีเจ้าของร้านและผู้ช่วยร้าน | เพียงพอสำหรับ MVP; บังคับสิทธิ์ที่ backend และซ่อนการกระทำบน UI ให้ตรงกัน |
| การขาย/คืนของ | บิลตัดสต็อกทันที และแก้บิลได้ | สำหรับระยะนี้พอ; อย่าใช้ “แก้บิล” เป็นวิธีแทนการคืนของในอนาคตโดยไม่ออกแบบสถานะ/หลักฐานการคืน |

## Flow UX ที่ควรยึด

1. **เริ่มจากงานที่ผู้ใช้ต้องทำ:** หน้าแรกแสดง ดูสต็อก / ออกบิล / จอง / รับของเข้า พร้อมสถานะที่ทำต่อได้จริง ถ้ายังไม่มีรุ่น ให้ปุ่มพาไปตั้งค่ารุ่น และอธิบายเหตุผลที่งานขายยังใช้ไม่ได้
2. **รักษาบริบทระหว่างหน้า:** เลือกรุ่นและตัวเลือกสินค้าแล้วกลับสู่บิลหรือการจองเดิมโดยไม่ทิ้งชื่อลูกค้า/จำนวน; จากแจ้งยอดต่ำกว่าจอง ให้ไปการจองของตัวเลือกสินค้านั้นและกลับมาปรับยอดได้
3. **หนึ่งผลลัพธ์ต่อหนึ่งการกระทำ:** หลังบันทึกแสดงรายการที่เพิ่งสร้างจริง พร้อมชื่อคน ยอด เวลา และยอดสต็อกหลังทำ ไม่กระโดดไปข้อมูลตัวอย่างคนละรายการ
4. **แยกจำนวนให้ชัด:** “ในร้าน”, “จองไว้”, “ขายได้” ต้องอยู่ด้วยกันในงานที่เสี่ยงขายซ้ำ ป้อนยอดปรับเป็น “จำนวนที่นับได้จริง” ไม่ใช่ส่วนต่าง
5. **ทางแยกต้องมีผลต่าง:** ยืนยัน/ไม่ยืนยันการยกเลิกต้องเปลี่ยน/คงสถานะแตกต่างกัน และแจ้งเหตุผลเมื่อยกเลิกไม่ได้
6. **มือถือระหว่างขาย:** ปุ่มยืนยัน ยอดรวม และข้อความผิดพลาดต้องยังมองเห็นหรือเข้าถึงง่ายเมื่อฟอร์มยาวและแป้นพิมพ์เปิด

## สิ่งที่ควรทดสอบกับร้านเพิ่มก่อนขยาย

- ร้านอื่นใช้หน่วย “แพ็ก” และรูปแบบไซซ์/สีใกล้เคียงกันเพียงใด โดยดูจากบิลยี่ปั๊วและการพูดสั่งของจริง
- ชื่อที่ร้านเรียก “รุ่น” และ “ตัวเลือกสินค้า” เข้าใจตรงกันหรือไม่
- กรอกของเข้าหลายรุ่นในครั้งเดียวบนมือถือสะดวกพอหรือไม่; หากมีบิลกระดาษยาว ต้องพึ่งการพักงาน/บันทึกฉบับร่างหรือไม่
- ลูกค้าประจำสั่งทางอื่นนอกจาก LINE มากเพียงใด เพราะสถานะ “การจอง” ควรไม่ขึ้นกับช่องทาง
- การจองค้าง 2 วันช่วยจัดงานจริงไหม หรือร้านต้องการเห็น “ถึงกำหนดติดต่อ” แบบอื่น

## ขอบเขตระยะถัดไปที่ควรเผื่อในข้อมูล

การแกะแพ็กขาย คืนของ และส่งของบางส่วนถูกเลื่อนออกไปแล้ว ระยะนี้ยังนับสต็อกเป็นแพ็กตาม ADR-0001 จึงไม่ควรแอบรองรับการขายเป็นตัวใน UI หรือเปลี่ยนหน่วยสต็อกโดยไม่มีแผนย้ายข้อมูล แต่ควรเก็บรายการเคลื่อนไหวและความสัมพันธ์ระหว่างการจองกับบิลให้ชัด เพื่อออกแบบงานคืน/ส่งบางส่วนภายหลังได้

ต้นแบบกดได้เป็นเครื่องมือทดสอบความเข้าใจและการนำทาง ข้อมูลอยู่ในหน่วยความจำ ไม่มีการล็อกแถว การยืนยันตัวตน หรือการเก็บข้อมูลถาวร จึงยังใช้พิสูจน์กติกา concurrency และสิทธิ์ข้ามร้านไม่ได้
